# 沟通理解与当前方向

修改代码前先读本文。每轮交流后，理解新增信息与已有要求的共同方向，把新形成的判断与取舍更新到这里；相同方向不重复记账。完成后用实际代码和验证结果校正理解。本文保存用户意图、设计判断和当前进度，项目规范仍以 ProjectGuidelines 为准。持续维护这一个文件，不按每条消息新建文档。

## 核心方向

用户希望代码的职责和所有权可以直接读懂：跨功能共享的领域数据由 Model 唯一拥有，System 处理规则，Entity 负责节点和表现，具体角色及技能状态承载自己的特殊行为。每个角色的输入消费记录和状态局部计时仍属于对应运行实例，不提升成全局共享状态。沿用主流程 GGF 状态机和 GetData 注册关系，借鉴 QFramework 的分工，不另造架构容器，也不靠公共基类堆角色例外。

扩展性来自恰当的边界。新角色能声明自己的技能、输入和状态即可；不为尚未制作的角色提前堆接口、枚举和层级。技能状态应该读得到该招的完整行为与阶段，不能只剩转发到 Helper 或统一解释器的空壳。确有多个实际使用点的公共生命周期、时间推进和物理能力可以共用。

文件组织服务于阅读。同一个功能的小型配套类型可以放在一起，只有内容和职责确实复杂时才拆脚本或 partial。不要为了命名、目录、测试或“通用性”制造额外包装。调用次数只是检查抽象的线索，不能替代职责判断；也不能把问题 API 换个接口继续保留。

输入需要区分来源、按键事实、动作规则和物理执行。采样是 InputSystem 的职责；不同角色的数据要隔离，不能把全局系统里的“当前输入”错误共享给多个角色。技能数量与键位由角色登记决定，不能把当前悟空的三个快捷键变成共享层的容量上限。

生产 API 为游戏实际消费者服务，不为测试增加状态名、观测 getter 或专门路径。测试可以使用现有 GGF 状态与反射。生成内容、框架和插件的只读边界继续遵守；旧存档不加运行时兼容层。美术与官方玩法的既有约定见 ProjectGuidelines、OfficialReference 和 LegacyAssetMap，不在这里复制。

## 本轮理解：收拢技能与输入职责（2026-10-16）

这次反馈的共同问题是：此前虽然给技能取了独立状态名，仍然拆出了过多小对象，并让身体接口承担输入决策。目标是顺着“采样 → 角色匹配 → 激活 → 状态推进 → 物理表现”就能读懂完整流程，减少跨文件追踪。

当前采用的判断：身体接口提供身体事实和物理能力；技能匹配与普攻选择移出它。下穿平台包含碰撞检测和位移，是物理能力，可以保留；S+K 的识别不进入该物理方法。状态决定当前是否接受动作输入，角色决定具体组合，避免实体根据一串状态类型硬编码规则。

按动作名提供通用的按下、按住和松开采样；技能绑定使用动作名，不再使用固定三格数组。输入消费仍要按角色隔离，并确保交给活动技能的一次按下不会再触发新一轮扣费。三个默认快捷键只是当前项目映射，新增第四、第五个绑定不应修改共享采样逻辑。

技能登记归 SkillModel，移除独立 SkillSet 对象和文件；配套登记项随模型放置。SkillSystem 的学习、激活及执行生命周期合并到同一文件。时间游标收进技能状态基类，具体招式仍各自执行事件。火魔斩的完成回调要核对本次执行身份，避免状态复用后旧回调改动新招式。

这些是基于当前意图的实现判断，须通过调用关系、真实 GGF 状态和游戏运行验证；发现不合适时修正方案，不以逐项照做代替设计。

## 本轮理解：让名称和参数表达实际职责（2026-10-17）

新的反馈延续同一方向：先确认一个类型是否承担真实职责，再讨论名称。SkillInstance 改叫 Skill 仍不解决问题：正式悟空五招完全由 GGF 状态执行，旧类型的 Start / Advance / HandleInput / Stop 只有测试派生类实现。为预设后续角色保留第二套行为基类、工厂和后台调度，反而使测试证明一套正式游戏没有使用的设计。删除这层；每次施放只保留 SkillData 的编号、完成、重力和输入锁标志，随 SkillModel 定义。这个小数据类的保留理由是跨状态及特效需要借用同一次施放身份，不能只凭技能编号让旧回调影响新施放。

输入也不应为了替换自制类型而再造一层流程。上一轮以“原生事件不是帧快照”为由保留自定义快照，理由不充分；当前游戏按物理帧查询，直接使用 Godot Input 的按下、按住、松开方法即可，消费记录仍按角色隔离。InputEventAction 是原生动作事件，在需要事件输入或虚拟动作注入时直接使用；当前采样没有必要先查 Input 再人工拼装事件。删除自定义快照及转发，不为测试保留生产替代类型。技能后续输入由具体 GGF 状态读取，独立特效已经有自己的节点生命周期；未来真正需要持续、蓄力或多阶段行为时，放进负责它的实际状态或节点，不提前堆一套执行框架。

共同方向是减少没有独立功能的封装，让“输入查询 → 角色匹配 → 系统登记数据与扣费 → GGF 状态推进 → 实体表现”直接可读。Model 拥有共享数据、状态拥有阶段行为的边界不变；HeroInputContext 同样没有额外职责，角色匹配直接接收三个参数，当前状态通过 TryGetActionInput 提供输入窗口，不并存 Get/TryGet 两套 API。

这次对 AttackInstance 的反馈也适用于其他领域数据：名称应交代数据内容，不能用 Instance 掩盖职责；这不意味着把结果、参数、配置登记和真正推进流程的对象全部机械改成 Data。改名要贯通类型、参数、持有字段、调用处和测试反射：单份数据参数用 data，多份用 weaponData / armorData 等限定；长期持有的数据字段明确带 Data，不能只改类型而留下旧称。攻击包保留池化、出招快照和命中去重，命名为 AttackData；实际装备命名为 EquipmentData，装备唯一身份仍叫 InstanceId。数据对象不承担存档边界的配置校验；该校验归已有 SaveDataUtility，不为迁移另建包装或兼容别名。

集合的名称也要直接读出复数，并避免重复限定：背包面板里的 EquipmentData[] 用 m_EquipmentDatas，ProfileModel 的唯一背包用 EquipmentDatas；不再用单数 Data 掩盖集合，也不堆 Visible 等已由所在对象表达的前缀。界面名称遵循本项目实际框架契约：GGF 管理的窗口统一 XxxForm，战斗根窗口采用 BattleForm；内部区域用 Panel，独立资源条用 Bar，不把每个布局节点都变成 Form。改名贯通脚本、目录、场景、打开参数、源表与生成登记，保留脚本 UID 和数值 ID。

视觉反馈要核对完整控件的层次和布局，不能只证明某张图标正确就认定整片区域正确。左下栏采用明确的混合边界：左侧保留造三法宝、宠物、技能、背包、设置五入口，技能与无双使用已约定的造一资源，并适配造三布局。灰色空槽是未学习状态，但黑色长底板丢失和技能栏下移是真实装配错误；资源清理必须检查装饰层的视觉职责，不能只看它是否承载数据或动画。

## 当前进度

输入决策已移出身体接口，HeroInputContext 与自定义输入快照已删除。InputSystem 使用原生三项查询和按角色的 ConsumePress；状态决定输入窗口，实体匹配角色规则。Skill / SkillInstance / SkillExecution 行为基类已移除；SkillData 与 SkillDefinition 随 SkillModel 定义，ISkillActor 只保留节点能力契约。SkillSystem 处理学习、条件、单次扣蓝、登记与取消，GGF 状态处理招式，独立特效由 SkillEffectNode 自行推进。重复的活动集合、技能工厂、后台推进和空生命周期已删除；脚本迁移保留 UID。

本轮规则回归 Profile 154、Battle 186、Level 18 均通过；隔离构建 0 错误。测试随真实职责调整，删除只验证旧空壳派生实现的样例，保留真实五招与多阶段 GGF 交接、取消、旧回调隔离和费用回归。真实引擎技能专项 PASS、退出 0，覆盖五招输入、持续 W+J、跑攻、火魔斩两分支与命中、输入不排队、UI 同步及 GGF 音效；退出仍有既有框架释放异常。脚本扫描与构建完成，编辑器插件退出滞留后仅停止隔离进程。实际命令与结果见 [Validation](Validation.md)。此前整套 UI 在升级动画等待处超时，无窗口复核在恢复数字暂停断言失败；这两项仍未定位，不能因本次局部技能通过而宣称整套 UI 通过。其他角色的具体技能尚未制作。

AttackData、EquipmentData 及参数、字段、集合引用已贯通；BattleForm 的 Ge 绑定、Luban 登记与资源常量经原有工具生成。三组规则测试为 358 项通过，隔离构建 0 错误；真实前端导航、攻击流程与技能学习专项通过，两张源表经实际 XLSX Diff 解析器识别出预期的 2 格和 1 格变化。

左下栏已恢复旧工程 718.png 黑色长底板及条的装配，技能栏移至它上方；五个造三入口的素材和位置保留。已与造三官方 RoleInfo 完整导出核对，底图和题签逐像素一致；造一 11 格技能图集保持不变。空值、半满、满值真实渲染通过，默认隐藏满值动画。验证边界与既有错误见 Validation，规范正文未自行改写。
