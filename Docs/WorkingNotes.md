# 沟通理解与当前方向

修改代码前先读本文。每轮交流后，理解新增信息与已有要求的共同方向，把新形成的判断与取舍更新到这里；相同方向不重复记账。完成后用实际代码和验证结果校正理解。本文保存用户意图、设计判断和当前进度，项目规范仍以 ProjectGuidelines 为准。持续维护这一个文件，不按每条消息新建文档。

## 核心方向

用户希望代码的职责和所有权可以直接读懂：跨功能共享的领域数据由 Model 唯一拥有，System 处理规则，Entity 负责节点和表现，具体角色及技能状态承载自己的特殊行为。每个角色的输入消费记录和状态局部计时仍属于对应运行实例，不提升成全局共享状态。沿用主流程 GGF 状态机和 GetData 注册关系，借鉴 QFramework 的分工，不另造架构容器，也不靠公共基类堆角色例外。

扩展性来自恰当的边界。新角色能声明自己的技能、输入和状态即可；不为尚未制作的角色提前堆接口、枚举和层级。技能状态应该读得到该招的完整行为与阶段，不能只剩转发到 Helper 或统一解释器的空壳。确有多个实际使用点的公共生命周期、时间推进和物理能力可以共用。

文件组织服务于阅读。同一个功能的小型配套类型可以放在一起，只有内容和职责确实复杂时才拆脚本或 partial。不要为了命名、目录、测试或“通用性”制造额外包装。调用次数只是检查抽象的线索，不能替代职责判断；也不能把问题 API 换个接口继续保留。

输入需要区分来源、按键事实、动作规则和物理执行。采样是 InputSystem 的职责；不同角色的数据要隔离，不能把全局系统里的“当前输入”错误共享给多个角色。技能数量与键位由角色登记决定，不能把当前悟空的三个快捷键变成共享层的容量上限。

生产 API 为游戏实际消费者服务，不为测试增加状态名、观测 getter 或专门路径。测试可以使用现有 GGF 状态与反射。生成内容、框架和插件的只读边界继续遵守；旧存档不加运行时兼容层。美术与官方玩法的既有约定见 ProjectGuidelines、OfficialReference 和 LegacyAssetMap，不在这里复制。

## 本轮理解：收拢技能与输入职责（2026-10-16）

这次反馈的共同问题是：此前虽然给技能取了独立状态名，仍然拆出了过多小对象，并让身体接口承担输入决策。目标是顺着“采样 → 角色匹配 → 激活 → 状态推进 → 物理表现”就能读懂完整流程，减少跨文件追踪。

当前采用的判断：身体接口提供身体事实和物理能力；技能匹配与普攻选择移出它。下穿平台包含碰撞检测和位移，是物理能力，可以保留；S+K 的识别不进入该物理方法。状态决定当前是否接受动作输入，角色决定具体组合，避免实体根据一串状态类型硬编码规则。

按动作名提供通用的按下、按住和松开采样；技能绑定使用动作名，不再使用固定三格数组。输入消费仍要按角色隔离，并确保交给活动技能的一次按下不会再触发新一轮扣费。三个默认快捷键只是当前项目映射，新增第四、第五个绑定不应修改共享采样逻辑。

技能登记归 SkillModel，移除独立 SkillSet 对象和文件；配套登记项随模型放置。SkillSystem 的学习、激活及执行生命周期合并到同一文件。动作时点交给原生动画，具体招式仍由各自状态执行规则。火魔斩的完成回调要核对本次执行身份，避免状态复用后旧回调改动新招式。

这些是基于当前意图的实现判断，须通过调用关系、真实 GGF 状态和游戏运行验证；发现不合适时修正方案，不以逐项照做代替设计。

## 本轮理解：让名称和参数表达实际职责（2026-10-17）

新的反馈延续同一方向：先确认一个类型是否承担真实职责，再讨论名称。SkillInstance 改叫 Skill 仍不解决问题：正式悟空五招完全由 GGF 状态执行，旧类型的 Start / Advance / HandleInput / Stop 只有测试派生类实现。为预设后续角色保留第二套行为基类、工厂和后台调度，反而使测试证明一套正式游戏没有使用的设计。删除这层；当时保留的小施放包装仍缺乏独立职责，现已进一步删除；旧通知的有效性归实际接收状态。

输入也不应为了替换自制类型而再造一层流程。上一轮以“原生事件不是帧快照”为由保留自定义快照，理由不充分；当前游戏按物理帧查询，直接使用 Godot Input 的按下、按住、松开方法即可，消费记录仍按角色隔离。InputEventAction 是原生动作事件，在需要事件输入或虚拟动作注入时直接使用；当前采样没有必要先查 Input 再人工拼装事件。删除自定义快照及转发，不为测试保留生产替代类型。技能后续输入由具体 GGF 状态读取，独立特效已经有自己的节点生命周期；未来真正需要持续、蓄力或多阶段行为时，放进负责它的实际状态或节点，不提前堆一套执行框架。

共同方向是减少没有独立功能的封装，让“输入查询 → 角色匹配 → 系统登记数据与扣费 → GGF 状态推进 → 实体表现”直接可读。Model 拥有共享数据、状态拥有阶段行为的边界不变；HeroInputContext 同样没有额外职责，角色匹配直接接收三个参数，当前状态通过 TryGetActionInput 提供输入窗口，不并存 Get/TryGet 两套 API。

这次对 AttackInstance 的反馈也适用于其他领域数据：名称应交代数据内容，不能用 Instance 掩盖职责；这不意味着把结果、参数、配置登记和真正推进流程的对象全部机械改成 Data。改名要贯通类型、参数、持有字段、调用处和测试反射：单份数据参数用 data，多份用 weaponData / armorData 等限定；长期持有的数据字段明确带 Data，不能只改类型而留下旧称。攻击包保留池化、出招快照和命中去重，命名为 AttackData；实际装备命名为 EquipmentData，装备唯一身份仍叫 InstanceId。数据对象不承担存档边界的配置校验；该校验归已有 SaveDataUtility，不为迁移另建包装或兼容别名。

集合的名称也要直接读出复数，并避免重复限定：背包面板里的 EquipmentData[] 用 m_EquipmentDatas，ProfileModel 的唯一背包用 EquipmentDatas；不再用单数 Data 掩盖集合，也不堆 Visible 等已由所在对象表达的前缀。界面名称遵循本项目实际框架契约：GGF 管理的窗口统一 XxxForm，战斗根窗口采用 BattleForm；内部区域用 Panel，独立资源条用 Bar，不把每个布局节点都变成 Form。改名贯通脚本、目录、场景、打开参数、源表与生成登记，保留脚本 UID 和数值 ID。

视觉反馈要核对完整控件的层次和布局，不能只证明某张图标正确就认定整片区域正确。左下栏采用明确的混合边界：左侧保留造三法宝、宠物、技能、背包、设置五入口，技能与无双使用已约定的造一资源，并适配造三布局。灰色空槽是未学习状态，但黑色长底板丢失和技能栏下移是真实装配错误；资源清理必须检查装饰层的视觉职责，不能只看它是否承载数据或动画。

技能反馈的重点是区分可调整的玩法数据、动作编排和招式规则。已删除 KnockbackFromCenter，以及同类的 GroundOnly、ConsumesSecondAirJump、Condition、Direction、Anchor；地面资格、跳跃消耗、火魔分支与落地条件由具体技能决定。独立特效也不能默认套用悟空的中心击退，必须由具体状态传入本次中心坐标。上一轮仍认可时间标记与素材装配留表的判断不充分：删除开关后，表格指令和解释器仍使状态难读，不能把局部删字段当成职责调整完成。

本次继续收敛到“数值表保存费用、伤害和明确的平衡参数；原生 AnimationLibrary/场景编辑动作时点和视觉；具体 GGF 状态执行招式规则”。用户已明确允许方法轨道；迁移后又明确要求同步规范，第 30 章旧限制现已修订。已查原生 Godot API、GDQuest 判定/连段源码和官方 TPS 实现，不能将它们的输入缓存、网络或架构照搬。审查覆盖原有全部 21 张业务表及 3 张 Schema：已删除三张技能编排表与混装 DropConfig，另将 SkillHitConfig 合入 AttackConfig 后删除；其余表的动画、声音、图标与界面时序也已迁回实际资源，不能只删几张表就声称完成。SkillTimelineKind/双游标一并清理，不改名成 Resource 再造解释器；节点只连接原生动画方法与当前具体状态，公共层不出现角色例外。普通状态的物理推进、临时输入与重力恢复仍由实际状态拥有。

同类 xlsx 按编辑职责合并成一个工作簿多个 Sheet，减少散落文件；这与删除表现表是两件事，不能只把旧指令表搬进一个大文件。按最新角色边界组织 Hero/Enemy/Skills/Combat/Items/Resources，独立关卡、建档和三类 Schema 保留，共 11 个；Enemy 为后续 BOSS 共用工作簿，不提前新建空表；合表后为 16 张业务表。保留表的生成名和稳定 ID，用 SheetName@文件明确绑定每张 Luban 表；删除表不留兼容层。迁移后的实际编辑位置与分工见 ProjectTour，不新增另一份重复规划文档。

从策划工作出发检查，而非从程序读取方便出发：截图中的缩放、偏移、镜像、场景路径和声音时点应在可预览的场景/动画中编辑；修改火焰大小不应该需要填 Excel 再导表。伤害阶段关联由具体出招方法明确指定，伤害数据本身仍在数值表。是否能自然地在正确工具中完成一次修改，是此次清理的验收标准。

同步官方要检查从原始参数到最终运动的完整链路。技能表的击退字典虽然正确，旧项目换算、缺失的横向衰减、怪物重力和受击时长都会改变表现；物理积分先后也会改变挑高。当前按造一速度×24、重力×24²换算，用秒制指数衰减和首步积分换算复现源轨迹，不虚构怪物质量系数，也不退回按渲染帧运行。

## 当前进度（2026-10-18）

输入按“原生查询 → 本角色消费记录 → 角色匹配 → SkillSystem 单次校验扣费 → GGF 身体状态”运行。模型从主流程 GetData 注册取得，SkillModel 唯一拥有技能书、登记和 ActiveSkillId；不再创建只有编号的 SkillData。阶段重力/完成归状态，输入锁归本英雄动作数据并由火魔状态对称设置/解除。旧 Skill/SkillInstance 行为对象、工厂、后台调度、自制输入快照与 HeroInputContext 均已删除，不为未制作的角色预建执行框架。

五招与五个独立效果已改用原生 AnimationPlayer 方法/属性轨道；状态负责招式规则，实体方法只接线。自建时间线解释器、编排枚举、双游标与逐帧 Seek 已清理。1424 个原值键、动画长度、判定形状与身体/武器原点经原生对照保持；本轮未重新生成图集。过时的一次性技能导入脚本在写入前拒绝覆盖已编排动画。

配置从 24 个旧 xlsx 整理为 11 个工作簿、16 张业务 Sheet；按最新要求分为 Hero 与 Enemy，Enemy 为后续 BOSS 共用工作簿，不建占位空表。四张表现/混装表删除，技能伤害并入 AttackConfig 后删除第五张表。Luban 正常导出并清理旧类/枚举/bytes；不手改生成物，不留兼容路径。物品外观由一个共享资源供背包/穿戴/掉落使用，轨迹、声音、音乐、血条淡出与演出时序回到实际场景和动画。

AttackData、EquipmentData、复数成员与 BattleForm 已贯通；左下栏仍保留造三五入口和黑色长底板，技能/无双使用约定的造一资源。GGF 窗口按 Form、完整内部区域按 Panel 组织；没有重建过细的 Footer/Column/按钮脚本。

反馈的共同方向是从编辑者的真实工作判断职责，并参考成熟项目的实际资源与脚本，而不以“查过资料”代替落地。GDQuest 的动画方法/属性轨道分工已用于正式五招；GGF 状态、节点池、音频与 Model/System 所有权继续沿用。三组规则测试最终 194/142/18，共 354 项通过；隔离完整构建 0 错误。60/120Hz 五招与火魔两分支、七段命中×三种怪物及真实轨迹通过；普攻第四段松手、掉落/背包、无双演出、血条复用和死亡动画结算专项通过。11 个工作簿的 XLSX Diff 两种解析均通过。

其他角色的正式招式尚未制作；专项不代表整套 UI 的既有无关失败已经消失。编辑器插件与运行退出时的既有框架异常保留，未修改只读依赖。命令、日志、验证范围及限制见 Validation；第 10/20/30/60 章已按本轮授权同步命名、动画时点与状态所有权。

## 动画回调的职责与命名（2026-10-18）

这次反馈的核心仍是让原生工具真正承担编排，而不是把旧代码套上“动画回调”的名字后继续保留双份职责。声音用一个编号入口；受击、死亡不再各加接口和包装。动画回调统一 AnimEvent 后缀，入口多时用 AnimationEvents partial，普通信号 On... 和具体状态方法保持各自语义；用户追问后缀，是希望从名字读出调用来源，不是为了机械移动单词。

此前将 InventoryFormData 视作无效包装并删除，混淆了窗口输入契约与运行时空壳；已按用户纠正恢复。需要打开参数的 Form 保留各自 Data，即使只有一个引用，不需要参数的窗口不建空 Data。删除 SkillData 后不再找另一个类型替代它：模型只记激活编号；火魔的旧完成通知利用既有 FSM/状态/EnterSerial 验证，特效节点无需理解施放身份。中断统一应用资源已有 RESET，固定节点用场景绑定，角色专属动画名在对应状态定义，避免用常量桶掩盖职责。动画决定发生时点；死亡收益、资源释放和取消仍归真实业务生命周期，不能被可跳过的表现牵制。

本轮清理已落实并验证：354 项规则测试通过；隔离完整构建、原生回调绑定、2424 个值键/48 个时点对照、五招及声音/RESET、背包复用、死亡结算和普攻专项通过。修复了运行验证发现的悟空场景缺失动作列表/命中声绑定；框架既有退出异常不在本次修改范围。详细命令、日志和限制仍只维护在 Validation。

本次理解是区分“边界上的约定”与“没有职责的封装”：FormData 给窗口明确的输入契约，不能因为成员少就删除；SkillData 只有重复的激活编号则没有同样的职责。技能面板的 V 开关复用输入映射、HUD 请求和窗口自己的暂停输入，避免用物理键判断或让实体直接开窗。业务场景文件统一 snake_case，类型与根节点保持 PascalCase；路径、源表、生成常量及验证一起更新，保留 UID，不改框架只读绑定。

继续审查配置时，以实际消费者判断数据归属，不能把所有战斗字段都当成表现。EquipmentDropPoolOverride 实际选择奖励池；它的配方覆盖只有花果山守关大猩猩使用，已删除覆盖、UseMonster 哨兵和跨事件重复传递，当前大猩猩的“不掉装备”统一写在怪物基础表。现有关卡奖励保持，未来若有真正不同的奖励规则再按需求设计。FeaturedOpponentId 则只决定顶部血条，已改为关卡场景绑定生成点，不影响怪物行为与配方数值；没有实际消费者的 Rank 及枚举一并删除。保留用户明确要求的生命/防御/攻击倍率与守关 25 经验。清理的目标是让修改发生在正确的所有者，而不是把字段机械从 Excel 搬进代码。

FormData、V 开关和配置复核已通过规则、原生场景与实际运行验证。此前旧名重复场景现已不存在，正式资源引用和 23 个暂存几何节点检查通过。资源改名还须同步编辑器的打开场景、最近记录与按路径保存的折叠状态；只改正式引用不够。Level_1 启动警告已定位到这些缓存，用户关闭编辑器后已备份并修复正式缓存，两次实际工程冷启动均无大小写警告，场景内容与 UID 保持。引用工具现按磁盘实际名称逐段检查大小写，避免 Windows 掩盖同类问题；不修改业务逻辑或只读依赖。具体命令与限制见 Validation。
