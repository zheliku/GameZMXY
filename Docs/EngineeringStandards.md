# 工程规范模板（Engineering Standards Template）

> 定位：从实际项目提炼的**可复用工程规范模板**，面向 C# 游戏项目（当前按 Godot 4.x 落地）。复制进新仓库后可整体裁剪；语言 / 工程类章节与引擎无关，标注「引擎相关」的章节换引擎时整节替换。
> 本文件**不参与**任何项目的 `AGENTS.md` 裁决链：在具体项目里，强制规则以该项目的 `AGENTS.md` 链为准；本文件是"怎么做"的起点。
> 文中 `示例：` 前缀均为某个具体项目的做法，只作说明，不是通用要求。

## 0. 核心方针（一句话版）

> 全部规范的凝练；详细规则见对应章节，冲突时以详细章节为准。

1. **人类裁决**：规范冲突停下报告，规范变更只由人类发起（§1）。
2. **双层分离**：纯逻辑层不引引擎类型，保证可单测、可复用（§3、§5.1）。
3. **单一入口**：引擎能力只走门面，禁自造单例 / 全局（§3、§5.2）。
4. **生成物隔离**：工具生成目录禁手改，重新生成即覆盖（§3、§5.3）。
5. **数据驱动**：数值唯一真相源在配置表，代码只写逻辑（§6）。
6. **池化**：高频生灭对象走池，禁裸实例化 + 销毁（§5.6）。
7. **状态机**：状态由状态机表达，代码是唯一的逻辑执行者与时钟，动画只是数据（§7）。
8. **引用不穿透**：跨模块走事件或显式注入，禁爬场景树（§5.8）。
9. **设计先调研**：新逻辑 / 新架构先看知名项目怎么做，再结合当前框架落地（§2）。
10. **整体性修改**：任何修改先纳入整体设计，禁补丁式叠加（§5.9、§9）。
11. **规范成文化**：目录沉淀出特有约定，及时写进该目录 AGENTS.md（§1）。
12. **验证闭环**：编译 → 导表 → 冒烟 → 提交前检查，缺一不可（§10）。
13. **重写不复刻**：旧代码只作设计参考，理解后按新架构重写（§5.4）。

## 1. 规范体系怎么搭

- 规范分层维护：**全局一处、目录就近**。根 `AGENTS.md` 写全局规则，各目录 `AGENTS.md` 只写本目录特有约定，不复制根规则（避免两份漂移）。
- 阅读顺序：任务开始先读根规范；改动落在某目录时，再读该目录及其祖先目录的 `AGENTS.md`（就近优先）。
- 冲突裁决：根规范 > 目录规范 > 推断。**发现规范与现实冲突时停下来报告**，由人类更新规范，AI 不擅自改规范。
- **目录规范及时成文**：某目录 / 路径沉淀出特有约定（重复出现的口头规则、特殊限制、新人会踩的坑）时，及时**添加或更新该目录的 `AGENTS.md`**——先查根规范与祖先目录规范是否已覆盖，只写本目录差异，不复制根规则。
- 成文时机判据：同一条约定**第二次被口头重复**时，就该成文；约定不成文，等于不存在。
- 每次交付说明三件事：改了什么、依据哪条规范、如何验证（构建 / 运行 / 测试结果）。
- 规范只描述"怎么做事"，不记录"做过什么"；历史沿革放项目文档或 commit message。

## 2. 设计与调研方针（新逻辑 / 新架构动手前）

设计不是从零发明：先看成熟项目怎么做，再结合本项目落地。

- **调研先于设计**：设计新系统、新状态机、新数据流时，先联网检索 2~3 个知名项目 / 成熟框架的同类实现，看它们的**流程与职责划分**（不是抄代码）：数据放哪、状态放哪、谁持有引用、怎么扩展。示例：状态机裁决前参考过 Celeste（全代码计时）、tModLoader `aiStyle`（行为分层）、Unity 社区对"动画事件驱动核心玩法"的警示。
- **结合框架落地，不生搬**：外部方案逐条对照当前项目的框架门面与目录结构再取舍（示例：GGF 的 `GF.*` 门面、bundle 目录约定）；确需偏离处说明理由。调研结论写进交付说明：参考了什么、为什么这么选、为什么不照搬。
- **适配既有结构**：新设计必须回答"放进现有目录树的哪里、依赖方向是否不变"；需要新目录 / 新层级的，先定职责写进规范（§1），再写代码。
- **先穷尽再新增**：动手前先看既有实现能否通过换参数 / 换组合 / 覆写一个虚成员满足；只有含真实差异时才新增。
- **质量标准（四词）**：**统一**（同类问题只有一种解法，不并行两套）、**规范**（遵循本仓库既有约定，不另起炉灶）、**清晰**（每个类 / 模块的职责一句话说得清）、**简练**（无冗余层级、无转发包装、不预埋用不上的抽象）——向高水平开源项目的设计水准看齐，能删的都删掉。

## 3. 工程结构原则

- **双层分离**：纯逻辑层（公式、结算、AI 决策、状态数据）与引擎桥接层（节点、场景、输入、渲染）分开；纯逻辑层不引用引擎命名空间，保证可单元测试、可跨引擎复用。
- **单一入口**：引擎能力只通过框架门面 / 服务访问（示例：`GF.组件`），禁止自造 Autoload 单例、静态全局变量、上帝类。
- 目录职责写进规范的"仓库结构"节；新增目录先定职责再写代码；未建目录标"按需创建"。
- **生成物隔离**：工具生成目录（配置代码、脚本半类、路径常量）禁止手改；业务逻辑只写在手写目录 / 半类里。
- 资源目录固定且数量有限，禁止"哪里方便放哪里"；不自建平行资源目录（示例：`Assets/`）。
- 第三方代码（引擎、插件、vendored 工具）原则上只读；确需修改走"例外记录 + 最小改动 + `[MODIFIED]` 标记注释"流程。

## 4. C# 编码规范

| 对象 | 规则 | 示例 |
| ---- | ---- | ---- |
| 类 / 结构 / 枚举 / 接口 | PascalCase，接口加 `I` | `WukongEntity`, `IDamageable` |
| 方法 / 属性 / 事件 | PascalCase | `TakeDamage`, `MaxHp` |
| 私有 / 受保护字段 | `m_` + camelCase | `m_Hp`, `m_SkillCdDict` |
| 引擎绑定字段（`[Export]` 等） | 同 `m_` 前缀约定 | `m_Body`（场景节点引用） |
| 参数 / 局部变量 | camelCase | `elapsedSeconds` |
| 常量 | PascalCase（`const` / `static readonly`） | `MaxLevel` |
| 命名空间 | `<产品>.<领域>` / 配置命名空间 | `GameLogic.Entity`, `GameConfig` |

- 一个文件一个主要类，文件名 = 类名；标识符只用英文，中文只出现在配置 / 文本资源。
- 数值类型统一：整数用 `int`，倍率 / 概率用 `float`；避免隐式截断的混算。
- 日志用条件编译日志封装（`Log.Debug / Info / Warning / Error / Fatal`），零开销；业务代码禁止 `print` / `Console.WriteLine`；自动化工具的 stdout 协议输出（如 `SMOKE PASS/FAIL`）例外。
- 异步框架坑（通用形态）：
  - 异步 API 命中缓存时可能**同步完成**——先注册回调 / 先建 `TaskCompletionSource`，再调用；
  - 池化事件参数在分发返回后立即回收——不可存字段 / 闭包，`await` 之后不可再读，跨层转发必须复制新实例；
  - 实现池化接口（`IReference` 等）的对象用完必须归还，同实例不可重复归还。
- 涉及实体死亡 / 切场景的 `async` 流程带取消令牌，避免回调打到已释放对象。
- 池化事件参数类的固定形状（示例：GGF `GameEventArgs`）：
  - `sealed` 类 + `static readonly int EventId`；属性全部 `private set`，对外只读；
  - 静态工厂 `Create(...)` 从池获取并逐字段赋值；跨层转发用复制工厂 `Create(source)` 新建实例，禁止直接转发原对象；
  - `Clear()` 把**每个**字段复位到类型默认值 / 安全值——新增字段漏复位，下次取用就是脏数据；
  - 只携带**值拷贝**：不引用其它池化对象（分发时可能已被回收）、不引用实体节点（可能同帧销毁）。
- 纯逻辑层确定性：随机数、时间等外部输入由桥接层取好**当参数传入**，纯逻辑层不自己取随机 / 读钟——结算确定、可精确单测复现。
- 基类不给"静默默认值"掩盖漏实现：关键契约用 `abstract` / 显式抛错，而不是默默返回 0 让 bug 晚暴露；反过来，只有所有子类都有的成员才进基类，不预埋用不上的字段。
- 禁一行转发包装：只做改名 / 挪调用点的包装方法一律不写；提取复用必须含真实逻辑且已有 ≥2 处真实使用。

## 5. 架构红线（违反一律返工）

1. 纯逻辑层禁止引用引擎类型。
2. 框架能力只走门面调用，禁止自造单例 / 静态全局。
3. 生成代码禁止手改，重新生成即覆盖。
4. 禁止逐行移植 / 翻译旧代码：理解设计后按新架构重写。
5. 禁止硬编码数值：属性、系数、掉落、刷新规则全部进配置表。
6. 高频生灭对象必须池化（子弹 / 飘字 / 特效 / 掉落物），禁止裸实例化 + 销毁。
7. 状态必须由状态机表达，禁止多个 bool 标志位拼状态、禁止巨型 `if / match` 分支链。
8. 禁止跨场景树穿透（`GetParent().GetParent()`、跨模块长链 `GetNode`）；用事件或显式注入。
9. 禁止补丁式修改：任何修改先纳入整体设计再动手（详见 §9 修改纪律）；在旧逻辑上叠特判、复制粘贴近似代码块、留死代码"以防万一"，一律返工。

## 6. 数据驱动与配表

- **唯一真相源**：数值只存在于配置源文件（xlsx 等），代码只写逻辑。
- schema 规范：每张表有中文名 / 说明列；多行表有主键；每个字段写中文注释（进生成的代码文档）；有历史对应物的表带溯源列（旧 ID / 旧键名）。
- 枚举值**显式写死**，不靠自动递增——插入一项会让后续 Id 全部漂移。
- 行为归属：谁在什么时机触发，引用就配在**触发者那一行**，不另建"绑定表"。
- 关联表只在"链接有独立数据"或"多主体共享但参数不同"时建，否则用主体行上的列 / 序号表达。
- 流程：改表 → 跑导表脚本 → 生成的代码与数据一起提交；生成物禁手改；导出后必须编译 + 冒烟验证。

## 7. 状态机与动画（引擎相关）

示例：Godot 4.7 代码状态机 + AnimationPlayer 直驱纯数据。

- 分工：**代码状态机决定"在做什么"**（每状态一个类），是唯一的逻辑执行者与唯一的时钟；动画资源只放表现数据（帧/特效/判定几何），**无方法轨道、从不调用代码**。
- 动作时长在初始化时从动画资源**读长度**（数据），由状态用物理 dt 计时——编辑改长度自动同步，不会失步。
- 音效由状态钩子触发，音源 ID 查表；判定几何用值轨道关键帧（"哪一帧的几何"是数据）。
- 将来动画中途的时点（第 N 帧放子弹/脚步声）：用引擎的动画标记，代码读时间自己计时——作者权在动画编辑器，但仍是数据不是回调。
- **轨道完备性**：直驱播放不回卷轨道——库内任一动画写过的值轨道路径，每个动画都必须带，否则切换后残留上一个动画的值。
- 打断优先级集中写在状态基类（死亡 > 受击 > 本状态决策），派生状态只写自己的决策；禁止 bool 标志位拼状态、禁止巨型 if 链。
- 纯逻辑状态机（AI 决策、身体动作）与动画无关：通用 FSM（每状态一个类）按帧驱动；物理相关的状态与 `MoveAndSlide` 同频驱动。

## 8. 资源管理

- 命名：小写 snake_case、语义完整、**全文件名唯一**（资源索引 / 常量生成器遇到重名会中止）。
- 生成索引 / 常量视为 CI 的一部分：提交前跑一次，确保通过。
- 资源迁移：文件名保留原样 + **单独维护映射表**（旧路径 → 新路径 + 帧规格 / 备注），不逐文件重命名、不写脚本自动翻译数值。
- 移动 / 重命名只在编辑器内做（引用自动修复）；`.import` / `.uid` 边车文件提交进 git。
- 分包 / 导出规则由标记文件驱动，禁止"资源放 A、发布前拷到 B"的两步搬法。

## 9. 修改纪律（整体性原则）

修改不是在旧代码上打补丁，而是重新到达一个自洽的设计。

- **先读后改**：动手前读完整个类 / 模块及其调用点，理解当初的设计意图；不理解就改，改掉的不是 bug 是结构。
- **一次修改是一个整体**：签名变了，调用点、命名、注释、关联测试、相关文档**同一批改完**；"剩下的下次再说"不允许存在。
- **同域顺带修整**：过程中发现邻近的结构问题，小且同域的一并整理（保持本次改动内聚）；超出范围或有风险的记录下来报告人类——既不顺手大改，也不无视。
- **对称删除**：删功能时把它的数据、事件、配置列、文档、测试一起删干净；"暂时留着以后用"就是死代码。
- **特判是警号**：第三次为类似场景写 `if` 特判时停下——该提参数 / 提层级 / 提状态了，而不是写第四次。
- **重复三处前沉淀**：同一逻辑第三次出现前，抽成一处共享实现；抽出物必须含真实逻辑（禁一行转发包装，见 §4）。
- 补丁式修改的信号（出现任一即停）：新代码绕开既有抽象另走一条路、为单点需求加旁路开关、注释掉而不是删除、`TODO 后续统一`越积越多。

## 10. 验证闭环

固定顺序：**编译 → 导表 → 冒烟测试 → 提交前检查**。

- 编译：日常 `dotnet build`；新增源文件后跑引擎的完整构建命令。
- 冒烟测试：无头运行 + 脚本注入输入 + 断言**真实运行状态**（不是日志），输出 `PASS / FAIL` 协议；判定看 stdout，别只看退出码（框架关闭流程可能有既有 bug）。
- 提交前：跑资源索引生成；确认生成物与手写代码同步；逐文件 `git diff` 复核只含预期改动。
- 文档自检：规范内引用编号可解析（无断链）。

## 11. 反模式清单（踩坑提炼）

- 多个 bool 标志位拼状态（旧项目最大教训）。
- 动画缺值轨道 → 切换后残留上一个动画的值（表现为特效位置/缩放错乱）。
- 事件参数用完不复制转发 → 双重归还崩溃。
- 先调用异步 API 后注册回调 → 池命中时同步完成，丢事件。
- 硬编码路径 / 数值 / 枚举 → 配置改不动。
- 生成物手改 → 下次生成覆盖。
- "资源先放一处，发布前再拷" → 双份结构、引用漂移。
- 本地 dll 与 NuGet 包混用同一库 → 版本漂移（统一走一种引用方式）。
- 只记录"做了什么"不记录"验证结果" → 回归无法定位。
- 补丁式修改：特判叠特判、复制近似代码块、注释掉而非删除——结构烂在累积里。
- 生搬外部方案不结合当前框架——两套并行解法，维护双倍。
- 目录特有约定只口头传不成文——新会话 / 新人必踩。
- 一行转发包装越提越多——调用链变长，逻辑没变少。
- 基类静默默认值掩盖漏实现——bug 晚暴露且难定位。
- 事件参数新增字段漏进 `Clear()`——脏数据串场。

## 12. Git 与协作

- 主分支受保护；功能分支 `feature/xxx`、修复 `fix/xxx`、素材 `art/xxx`。
- 提交前缀：`feat: / fix: / refactor: / art: / config: / docs: / chore:`；一句话说清意图。
- 素材迁移单独 commit，不与逻辑改动混提。
- `.gitignore` 至少覆盖引擎缓存、构建产物（`bin/`、`obj/`）、`*.tmp`、IDE 本地配置（`.vs/`、`*.user`）。
- 规范变更只由人类发起；AI 发现规范与现实冲突时先报告，再继续。
